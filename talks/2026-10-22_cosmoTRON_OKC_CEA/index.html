cosmoTRON · OKC C&EA WG · grey = the DESC code that does the step

For the extragalactic folks: this is the catalogue-to-cosmology chain, with the name of the DESC code for each step in grey. You do not need the names; I will mostly say what a tool does. Start from a galaxy catalogue, pixelise into maps with masks, measure angular power spectra between redshift bins, build the covariance, put everything into one data file, and run a likelihood plus sampler to get posteriors. TXPipe is DESC's pipeline that chains steps 2 to 5. Every arrow is a hand-off with its own config and format, and every stage gets checked with null tests and mocks, with blinding until the end.

A 60-second primer

What is 3×2pt?

γ × γ

Cosmic shear

Shapes of source galaxies, sheared by all the matter in front of them. Spin-2 field.

δ × γ

Galaxy–galaxy lensing

Lens positions against source shapes: the matter around the lens galaxies.

δ × δ

Galaxy clustering

Positions of lens galaxies: the matter field, times the galaxy bias. Spin-0 field.

550 × 550

Tomography multiplies it: an LSST-Y1-like setup with 5 lens + 5 source bins gives 55 tracer pairs × 10 bandpowers in one joint covariance.

cosmoTRON · OKC C&EA WG

Quick primer for the non-lensing people. Three two-point functions from two fields: shear (spin-2) and galaxy density (spin-0). Combining them breaks the degeneracy between galaxy bias and the amplitude of matter fluctuations. Split galaxies into photo-z bins and you take all auto- and cross-spectra between bins: the number of pairs grows fast. The 550×550 example is the LSST-Y1-like cosmoTRON run we will see later.

The Stage-III lesson

7 years

from the last night of DES data to its final 3×2pt cosmology.

LSST: ten years of data, 18,000 deg², billions of galaxies.

We cannot afford the same pipeline lag.

The big motivation. DES finished observing in January 2019; the Y6 3×2pt results came out in January 2026. LSST will deliver an order of magnitude more data, with yearly releases. If every analysis choice still costs weeks of re-configuring and re-running bespoke pipelines, the analysis falls years behind the data. That is the problem cosmoTRON goes after.

cosmoTRON · OKC C&EA WG

For people who have only used a chatbot: a chatbot answers, an agent acts. You give it a goal and a set of tools (functions it can call), and it runs a loop: think about the next step, call a tool, read what comes back, think again, until it is done. In cosmoTRON the tools are the cosmology codes; the LLM only decides how to use them.

The idea

From one agent to a team

One agent doing everything

One long context: early decisions get forgotten.

Every tool on the table: easy to call the wrong one.

One huge transcript: hard to check.

A team of specialists

Each agent has one job and only the tools it needs.

Short, focused contexts: a mid-sized open model copes.

Every hand-off is a file you can check.

Catalogue-to-cosmology is programmatic, with checkable intermediate products: exactly the profile multi-agent systems are good at.

Config files beat bespoke scripts.

Natural language beats config files.

cosmoTRON · OKC C&EA WG

A multi-agent system splits the job the way a collaboration does: a planner, a data person, someone who runs the measurement, someone who checks systematics, a reviewer. Each one sees only what it needs. That is what makes it work on a local model rather than the biggest model in the cloud.

The core argument of the talk. Nine clicks. 1. The engine is the LLM. It is what everyone talks about, but on its own it goes nowhere. 2. The chassis is the harness, opencode: what holds everything together and talks to the engine. 3. Wheels, brakes and gearbox are the tools: the tested cosmology codes that actually touch the road, i.e. the data. 4. The on-board systems are the agents: each one manages one subsystem (planning, ingest, measurement, systematics, inference, review). 5. The driver is the researcher: you decide where the car goes, by writing the TASK.md. 6. The race engineer on the radio is the human at the gates: the plan, the systematics and the memory decision. 7. Telemetry: the manifest, the replay script and the citations, so every run can be inspected afterwards. 8. The rulebook: the SKILLS and workspace conventions every agent follows. 9. Most of cosmoTRON is the car, not the engine. That is why it can run on a local open model, and why swapping the engine is a config change we can test.

The idea

Why local, open models?

Reproducible

Pinned weights never change under you: the same engine in five years.

Data stays home

Unreleased survey data never leaves the machine.

Cheap to repeat

No per-token bill: run the same TASK a hundred times to measure the agents’ own scatter.

Independent

No vendor can change, re-price or retire the engine.

The goal: a full analysis driven from workstation-class hardware, not a frontier cloud model.

cosmoTRON · OKC C&EA WG

Why insist on open weights served locally? Reproducibility: a hosted model can be updated or retired at any time, a downloaded one cannot. Data: collaboration data stays on our hardware. Cost: repeating runs is free, which is what you need to measure run-to-run reproducibility. Independence from any single vendor. Frontier cloud models work too (Claude Code is supported), but they are not the target.

Three ingredients. Tools do the numerics, deterministically. Skills are the written know-how (how to use the NaMaster API properly, how the workspace is laid out). cosmoTRON · OKC C&EA WG

Key design choice: the LLM never does the numerics. It plans and calls tools; the measurement (map-making, power spectra for spin-0 and spin-2 fields, deprojection, Gaussian covariance, assembling the data file) is done by the MCP tool server on top of standard, tested DESC codes. MCP (Model Context Protocol) is just the standard way to expose functions to an LLM. It is catalogue-agnostic: any galaxy catalogue with the required columns.

Nine agents, each with a narrow job and only the tools it needs: the on-board systems of the F1 car. The orchestrator is the entry point. The planner never runs anything without the human approving the plan. The reviewer is the last line: it judges a deterministic evidence block (not vibes), emits PASS/FAIL, proposes memories for future sessions, and writes the replay script and the citations file. The literature scout uses the MCP-ADS-arXiv server by estevesjh.

One slide, nine clicks (Present mode builds it step by step; edit view and PDF show the full chart). Start: the orchestrator reads TASK.md and the session bootstrapper creates the session folder, manifest and metadata. Click 1: the literature scout does a light ADS/arXiv lookup and writes a Science Context Block. Click 2: the planner reads the TASK, the context block and past memory, and drafts a plan. Nothing runs until a human approves; "no" sends it back. Click 3: on approval, the data ingestor reads DATA_DESCRIPTION.md, standardises the catalogue and registers it (or reuses one already in the registry). Click 4: the analysis coder runs the measurement tools in order: maps, power spectra, covariance, the SACC data file, plots. Click 5: in parallel, the systematics checker runs null tests (B/EB modes, c-terms, PSF leakage). If something shows up, a human decides. Click 6: the inference agent writes the likelihood (Firecrown) and sampler (CosmoSIS) configs; the job runner runs them locally or on HPC. Click 7: everything goes to the reviewer, which checks the evidence and says PASS or FAIL. Click 8: the reviewer proposes memories (human decides), writes CITATIONS.md and replay.py. Saved memories feed the next planner (dotted line).

From the C2C TASK.md: “Reuse the glass dataset if it is already in the registry.” Next: an L2 registry for nside-dependent products. The cosmotron-data-registry CLI also pushes catalogues to the HPC.

Cleaning and standardising a catalogue is the slowest, most error-prone part of the human workflow: mapping columns to roles, cuts, building per-bin catalogues and masks, measuring shape noise and number densities. cosmoTRON does it once. The standardised products go into the data registry, and the next time a TASK names the same data the ingestor reuses them and goes straight to the measurement. Masks are nside-dependent, so an L2 registry for nside-dependent products is next on the list. The cosmotron-data-registry CLI manages the registry and pushes catalogues to the HPC.

DATA_DESCRIPTION.md: GLASS 450

# The GLASS 450 Survey
- catalogue file: glass_cosmic_shear.fits
- redshift distributions:
  redshift_distributions_tomobin_0.dat,
  redshift_distributions_tomobin_1.dat,
  redshift_distributions_tomobin_2.dat
- theory cls:
  theory_cls/glass_theory_cls_{P}_bin{A}_{B}.txt
- survey footprint (reference only, NOT the
  analysis mask): survey_mask_N256.fits

## Probe & ingestion
- probe: galaxy_shear (spin-2, cosmic shear only)
- columns → roles:
    - RA → RA (deg)
    - DEC → DEC (deg)
    - PHOTO_Z → photometric redshift (reference;
      NOT used for binning)
    - G1 → e1 (ellipticity component 1)

    - G2 → e2 (ellipticity component 2)
    - SYST_WEIGHT → weight (inverse-variance
      shear weight)
    - ZBIN → tomographic-bin index (0,1,2)
- tomography: bin by the ZBIN column
  (bin_col=ZBIN, bin_values=[0,1,2]);
  do NOT use z_edges.
- mask: build a PER-BIN shear mask from the
  weights (mask_from_weights): mask = Σw where
  objects are present, 0.0 elsewhere. Do NOT use
  survey_mask_N256.fits as the analysis mask –
  it is a footprint reference only.
- sigma_e: measure per bin from the catalogue
  (no user value provided).
- Maximum usable multipole for this catalogue:
  Lmax = 256.

The data description travels with the catalogue: which file is what, which column plays which role, how to bin and how to build the masks. Whoever made the catalogue writes it once; every future task reuses it.

Why this matters: MCP tool calls have a hard timeout of about 60 seconds, so anything heavy (map-making on a big catalogue, covariances, MCMC) cannot run inside a tool call. cosmoTRON dispatches those steps as SLURM jobs on an HPC cluster, and the session can detach so you can close the laptop. When the job finishes, or a step needs an agent or a human decision, an ntfy.sh push notification arrives on your phone; you reattach with cosmotron-session and carry on. Still under testing.
